# Changelog

All notable changes to Kubebay are documented here.
Format based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versioning follows
[SemVer](https://semver.org/) once v1.0 is reached (pre-1.0: minor = breaking, patch = features/fixes).

## [Unreleased]

### Added
- **Click away to close a drawer**: a press anywhere on the page behind an open resource, pod or Helm drawer closes it, and a press on another row switches it to that row. Presses inside the drawer, in a menu or dialog it opened, in the YAML editor's own menus, in the ⌘K palette or on a right or middle click leave it open. The full-page view doesn't close this way
- **The namespaces you pick are kept**: each cluster's namespace selection outlasts a reload and a restart, so the Pods, workload and other lists come back filtered as you left them, and an identity that can't list namespaces doesn't name them again. It's kept on this machine. A kept namespace that has since been deleted stays ticked in the picker, marked "not on this cluster", so you can untick it (ADR 0003)
- **Kubebay works for someone who can see only some namespaces**: when your identity can't list namespaces (a Rancher project member, a developer on a shared EKS, GKE or OpenShift cluster), the namespace picker starts in your kubeconfig context's namespace instead of a cluster-wide list that never loads. It says "You can't list namespaces on this cluster. Showing the ones you named." with the API server's reason, offers no "All namespaces", and takes typed namespace names (checked to be valid names), which it remembers for that cluster and can forget. The Workloads Overview, which reads the whole cluster, offers "Open Pods in shop" instead of only saying what it can't list, and Topology offers your namespaces instead of `default`. Nothing changes for an identity that can list namespaces (ADR 0003)
- **Three more performance budgets measured in CI**: the `perf (kind)` job now also measures, on every pull request:
  - the time from a pod being created to its row painted on the Pods page (p95 of 30);
  - the frame rate scrolling a Pods table of 100,000 rows;
  - idle memory and CPU with three clusters connected and one open.
  
  After three stable runs on main, watch-to-paint and the three-cluster rows fail the build like the first four. Scrolling, within its budget but only just (57.4 to 60 fps against 55), still warns. The engine's memory with 100,000 pods, which CI doesn't run, was measured once by hand. `docs/PERFORMANCE.md` has the method and the numbers
- **The desktop app updates itself** (once releases carry the update signing key): 30 seconds after launch and once a day it checks the latest release, downloads a newer version in the background and verifies its signature, then shows an **Update ready** banner. **Restart to update** installs it, but never while a terminal, port-forward or change is in flight; the banner says which. Settings → Updates turns the checks off, shows the one URL they fetch (with no identifiers), and has **Check now**. A Homebrew cask install is told to `brew upgrade` instead. Builds without the key never check. The engine gains `GET /api/activity`, which reports what a restart would interrupt
- **Monthly download report**: a scheduled `download report` workflow writes, on the 1st of each month, how many times each release and channel (macOS, Windows and Linux apps, the engine tarballs that Homebrew installs, the air-gapped bundle) was downloaded, all time and since the previous report, plus stars and forks. It reads public GitHub data only: nothing in the app changes and nothing is sent from anyone's machine (`scripts/download-report.mjs`)
- **A ResourceClaim's page shows its allocation**: the Summary tab of a DRA ResourceClaim, opened from the ResourceClaims table or a pod's "Resource claims" link, now shows:
  - the claim's state and the device class it asks for;
  - each device it was given (pool/device, driver and the request it answers);
  - the pods it's reserved for, linked.
  
  It used to show only the claim's labels and annotations. The `e2e dra` CI job checks it against the DRA example driver
- **DRA tables tested against a real driver**: a new `e2e dra (kind, Kubernetes 1.37)` CI job installs the Kubernetes DRA example driver on kind. It checks the result in a real browser: the DeviceClasses, ResourceSlices and ResourceClaims tables show the driver's GPUs and an allocated, reserved claim, and the Pod drawer links the pod's claim
- **Performance measured in CI**: a new `perf (kind)` job measures the engine binary on every pull request against a kind cluster:
  - cold start to the web shell's first painted frame;
  - idle memory and CPU with one cluster open;
  - memory and time to load with 1,000 and 10,000 pods watched.
  
  It checks the results against the PRD's budgets, warning for now, and attaches the numbers to the run. `docs/PERFORMANCE.md` says how each number is taken and what it leaves out. `scripts/desktop-cold-start.mjs` times the desktop app from launch to its first painted frame, for each release. The README and PRD no longer say the budgets are unmeasured, or that a red metric fails the build
- **Golden-path E2E in CI**: a new `e2e (kind)` job runs a Playwright test in Chromium against the built engine and a kind cluster on every pull request. It connects with the session token, opens the cluster and Pods, checks that a pod's logs stream, runs `echo` through a shell in the pod, port-forwards to the pod and loads its page, then edits the pod's YAML, dry-runs it with a diff and applies it, and checks with `kubectl` that the cluster stored the edit. It also fails on any uncaught error in the page. See `docs/E2E.md`
- **Windows and Linux desktop smoke test in CI**: a new `desktop smoke` job builds the desktop app on `windows-latest` and `ubuntu-22.04` the way the release does, launches it with `KUBEBAY_SMOKE=1` (under Xvfb on Linux), and passes only if the engine sidecar starts and the web shell paints. In a smoke run the app exits 0 once the shell reports it has painted, and 1 if the engine never listens or 90 seconds pass. The page's IPC surface grows by one command, `smoke_ready`, which does nothing outside a smoke run. The README and website label the Windows and Linux apps **Preview** until a release is tested by hand on each. The website's Download section no longer links to installer names no release has, or offers `winget`, `install-linux.sh` or `helm repo add`, none of which exist. Windows and Linux link to the release page, and Helm installs the chart from the repository
- **Air-gapped install bundle**: each release gets `kubebay-airgap-<version>.tar.gz`. It holds the Helm chart with its image pinned to the release (never `latest`), the image for every platform as an OCI archive to push to a private registry, a per-platform archive for `docker load` / `ctr images import`, an offline install guide (`docs/AIRGAP.md`), and a `SHA256SUMS` with a keyless cosign signature. The tarball itself is attested and signed like every other release asset. Built by `scripts/airgap-bundle.mjs` in a release job that waits for the tag's image
- **Installer sizes per release**: the release workflow weighs every installer and archive (`.dmg`, `.exe`, `.msi`, `.deb`, `.rpm`, `.AppImage`, `.zip`, `.tar.gz`) against the previous release's, matched by name with the version taken out, and writes the table to the job summary. Each installer more than 10% larger gets a workflow warning, which becomes a failure once the budgets have three stable runs. The report is attached to the release as `installer-sizes.json` and signed with the other assets (`scripts/installer-sizes.mjs`, tested in a new `scripts (node)` CI job)
- **Dynamic Resource Allocation (DRA) tables**: a new "Devices (DRA)" sidebar group lists ResourceClaims (state as kubectl prints it: pending, allocated, allocated,reserved; the device classes asked for; the devices allocated as pool/device; the pods it's reserved for), ResourceClaimTemplates, DeviceClasses (with the driver their CEL selector pins) and ResourceSlices (driver, pool, the node, linked, or "all nodes", and device count). The Pod drawer's Summary lists the pod's resource claims and links each to its ResourceClaim, or says it isn't created yet. It reads `resource.k8s.io/v1`, GA in Kubernetes 1.34
- **Kubernetes 1.34 libraries**: client-go and the other `k8s.io` modules move from v0.31.4 to v0.34.10, and Helm from v3.16.4 to v3.19.5, the newest that still build with Go 1.24. CI runs the kind integration suite on Kubernetes 1.29, 1.34 and 1.37 (the 1.29 job was kind-action's unpinned default; it's now pinned), and a new integration test checks that DRA objects stream on clusters that serve them
- **Honest public claims**: the website's comparison table now comes from a typed data module (`website/src/data/comparison.ts`) in which every cell names its source and the day it was checked, and a website unit test (new `website (astro)` CI job, also run before each deploy) fails on a cell without one. The table keeps license, price, sign-in account and desktop app, each linked. Memory, start-up and installer-size rows are gone until Kubebay measures every tool the same way. Corrections: k9s is Apache 2.0, not MIT; Headlamp has a desktop app; k9s is a terminal UI; Lens's Personal plan is free under $10M revenue or funding. The hero, "Built to Perform" card, README and PRD no longer say the budgets are enforced in CI or quote an unmeasured 150 MB, 1.5 s or 40 MB: they quote the v0.6.0 installer sizes (19 MB Windows, 27 MB .deb, 53 MB universal DMG, 102 MB AppImage)
- **Extensions: your own columns and row actions**: `~/.kubebay/extensions.yaml` adds table columns (a JSONPath per resource) and row-menu actions to any resource's table, Pods included. A link action opens in the browser with the row's values percent-encoded into its path and query; its host is always the one you wrote. A command action opens Terminal on the row's cluster and types the command at the prompt without pressing Enter, with every value quoted as one argument (checked against bash, dash, zsh and fish with hostile names and annotations). Values with control or direction characters aren't typed, and a placeholder inside quotes is refused when the file loads. Placeholders: `{{name}}`, `{{namespace}}`, `{{kind}}`, `{{context}}`, `{{label:KEY}}`, `{{annotation:KEY}}`; an action can be limited to some contexts. Kubebay only reads the file, again on each Reload, so edits need no restart. Settings → Extensions shows what loaded and why any entry was skipped. Command actions need the local shell and a shell Kubebay quotes for (sh, bash, zsh, dash, ksh, fish). Extensions are off in in-cluster and OIDC modes. Resource-table JSONPath now also reads `[N]` indexes and `\.` inside keys. See `docs/EXTENSIONS.md`
- **StatefulSets and DaemonSets show their rollouts too**: their drawers get the Summary line ("Revision 4, rolled out 3d ago · 2 rollouts in the last 7 days") from their ControllerRevisions, and a Rollout tab with each revision's ready pods. Their rollbacks say when they happened ("rolled back to an earlier template 5h ago"), read from when the cluster last wrote that revision
- **Saved views**: every resource table has "Save view", which keeps the table as you left it under a name: cluster, kind, namespaces, filter (the `key:value` filter language), columns and sort. Views are listed under "Saved views" in the sidebar and in ⌘K, and opening one connects its cluster and restores all of it. They're kept on this machine, so they outlast a restart and a kubeconfig reload. Settings → Saved views lists and deletes them, and exports them to a `kubebay.savedViews` JSON file to share through git. An import is validated and replaces views with the same name, cluster and kind. Resource tables also honour a `?q=` filter in their link
- **Signed releases with build provenance**: release assets and the `ghcr.io/rajasardar/kubebay` image are signed keylessly with cosign (v2.6, by the release and publish workflows' GitHub identity) and carry GitHub build-provenance attestations. Each release asset gets a `<asset>.cosign.bundle` next to its `.sha256`. `docs/INSTALL.md` has a "Verify your download" section (`shasum`, `cosign verify-blob`, `gh attestation verify`), and the new chart README shows `cosign verify` for the image. Kubebay's own image-signature check names the signing workflow for its in-cluster image
- **Export a findings report**: the RBAC page's "Export report" saves every finding Kubebay's detectors have for the cluster as SARIF 2.1.0 (for code-scanning tools), JSON or Markdown. It covers attack paths, RBAC findings (system bindings left out, as on the page), API versions an upcoming release removes, single points of failure, pods no NetworkPolicy selects, Secrets read into environment variables, default-ServiceAccount token mounts, and namespaces where nothing enforces image signatures, each with its CIS and ATT&CK control IDs. The report names the cluster, the time and the Kubebay version (a new token-protected `/api/version`). The objects only the export needs (PodDisruptionBudgets, EndpointSlices, served API versions) load only while its dialog is open. The file is saved on this machine and sent nowhere
- **Rancher-aware clusters**: a context that goes through Rancher's cluster proxy (`https://<rancher>/k8s/clusters/<id>`) gets a "Rancher" badge on the cluster list, whatever its name, and an "Open in Rancher" row action that opens that cluster in the Rancher dashboard. Authorized Cluster Endpoint contexts, which reach the cluster directly, aren't labelled. The `rancher-desktop` context is badged "Rancher Desktop". In a cluster with Rancher projects, the namespace filter groups namespaces by project (`field.cattle.io/projectId`), with the rest under "Not in a project". Kubebay never uses a Rancher API token: the kubeconfig stays the only credential
- **Keyless image signatures are verified, and the signer is named**: the running-image signature check (RBAC page card and the workload, pod drawer Signatures tabs) now checks a keyless cosign signature the way cosign does against Sigstore's public instance, instead of leaving it to the admission controller. The Rekor entry's signed timestamp must verify with a Rekor key in Sigstore's trusted root, the entry must record this signature, certificate and payload, the certificate must chain to Fulcio at the time Rekor logged it and carry an SCT from a known CT log, and the signature must verify. The signer (email or workflow URI) and OIDC issuer are shown. They're then matched against the keyless identities in the cluster's Kyverno verifyImages attestors (subject/issuer, regexps, `*` wildcards) and Sigstore ClusterImagePolicy keyless authorities: a match is "verified by <policy>", a signer no identity allows is "verification failed" with who signed, and with no policy identity the verified signer is still shown. Identities that trust their own Fulcio roots or Rekor log are reported as not judged here. Sigstore's trusted root is fetched only when a keyless signature turns up, through TUF (go-tuf, starting from the root sigstore-go ships), reused for a day, and kept in `~/.kubebay/sigstore` so a check offline uses the last verified copy. With no copy and no network the signature is reported as not checked, and that answer isn't cached. OCI 1.1 Sigstore bundles are still found but not verified
- **When it last rolled out**: a Deployment's Summary tab says how old its current revision is and how many rollouts the last 7 days had, rollbacks included ("Revision 4, rolled out 3d ago · 2 rollouts in the last 7 days"), with a button to the Rollout tab. It reads the ReplicaSets the cluster keeps, so it needs no recording. A rollback reuses an older ReplicaSet, so it is named as a rollback rather than given an age, and when ReplicaSets pruned by `revisionHistoryLimit` hide part of the week the count says "at least"
- **Why a workload keeps breaking**: with history recording on, each broken hour now keeps its reason (CrashLoopBackOff, OOMKilled, ImagePullBackOff…), and after a recorded week the workload drawer's 7-day chip says so: "Broken in 9 of 166 recorded hours, on 5 of 7 recorded days, mostly: keeps crashing on start". It names a reason only when one is behind at least half the broken hours, and never a vague one (not ready, pending)
- **Assistants can propose changes; you approve them**: a new "Let assistants propose changes" setting under AI assistants (off by default) adds the MCP tools `propose_change` and `get_proposal_status`. A proposal is a strategic merge patch to a Deployment, StatefulSet, DaemonSet, CronJob, Service or Ingress in scope (`spec` and metadata labels/annotations only). Kubebay dry-runs it, changes nothing, and opens a dialog showing who proposed what, why, and the exact diff, with Approve and apply, Reject or Decide later. Approving applies exactly that diff as field manager `kubebay-mcp`, and only if the object hasn't changed since; otherwise the proposal goes stale. Proposals expire after 5 minutes. Scope is checked again at approval, only the Kubebay window can approve (never the MCP token), turning MCP or proposals off rejects whatever is waiting, and every step is audited. The assistant's copy of the diff has env values redacted
- **AI incident triage, step 2: Send**: when a key is set, the pod Triage tab's review pane has a "Send to <model>" button that makes exactly the request shown, once, with the Anthropic Go SDK. The engine reads no credentials or endpoint from its environment beyond the key it names, so the call goes where the preview says. The answer comes back as structured JSON: a summary, findings rated likely, possible or unlikely, each citing bundle sections by ID, next steps as text only, and what evidence is missing. Kubebay removes citations to sections that aren't in the bundle and hides findings left with none, and says how many it hid. Each finding shows the sections it cites. A refusal is shown as one, not as findings. Triage asks for `high` effort on models that take it. On Anthropic's own endpoint, for Claude Opus 5.5, Opus 5, Fable 5.1 and Sonnet 5.5, it asks for server-side refusal fallbacks (`fallbacks: "default"`), and the tab names the model that answered. A preview can be sent for 10 minutes, and Send checks again that triage is on for the cluster and the endpoint and model haven't changed. A failed send can be retried. Each send is audited as `triage:send` with the outcome and token counts
- **AI incident triage, step 1: consent and the review pane**: Settings → AI incident triage is off by default. It turns on per cluster, with a configurable endpoint (Anthropic's Messages API, or a proxy that speaks it over https; http only on this machine) and model. The API key goes to the macOS Keychain or libsecret, or comes from `KUBEBAY_TRIAGE_API_KEY` / `ANTHROPIC_API_KEY`, and is never written to settings. Pods in allowed clusters get a Triage tab that gathers a bounded evidence bundle: the pod and its owners, container states with the last exit, Warning events for the pod and its owners deduped with counts, the Deployment's recent revisions, and logs, with a restarted container's previous run first. The tab shows the exact request, with credentials masked and logs cut to about 12k tokens. Nothing is sent yet; the bundle can be copied. Each preview is audited. Not available in in-cluster or OIDC mode
- **MCP `get_logs` masks credentials** (tokens, keys, passwords in URLs and `name=value` pairs) with the same pass triage uses
- **Find AKS clusters**: the cluster list's Kubeconfig sources dialog also lists the AKS clusters your own `az` can see, in every resource group of the subscription you pick (az's current one first), and imports one with a click. Only clusters that sign in with Microsoft Entra ID import. The file Kubebay writes, `~/.kubebay/discovered/aks-<subscription>-<group>-<name>.yaml` (0600, context `aks_<first 8 of subscription>_<group>/<name>`, shown with the AKS badge and its cluster name), signs in with `kubelogin get-token --login azurecli`, so tokens come from your `az login` and no client certificate or token is stored. Clusters with local Kubernetes accounts are listed with the reason and no Import button. Kubebay reads the API server and CA through `az rest` (the same `listClusterUserCredential` call), not `az aks get-credentials`, which can run `kubelogin convert-kubeconfig` on your own kubeconfig. A cluster you already fetched with `az aks get-credentials` is recognised by its API server. Private clusters are marked. It's user-triggered only, desktop only, and az's errors are turned into the fix (sign in, the role it needs, an unregistered provider)
- **Find GKE clusters**: the cluster list's Kubeconfig sources dialog also lists the GKE clusters your own `gcloud` can see, in every location of the project you pick (gcloud's default first), and imports one with a click. The import writes `~/.kubebay/discovered/gke-<project>-<location>-<name>.yaml` (0600), named `gke_PROJECT_LOCATION_NAME` like `gcloud container clusters get-credentials`, signing in with `gke-gcloud-auth-plugin`, never a static token. It's user-triggered only, desktop only, and gcloud's errors are turned into the fix (log in again, enable the Kubernetes Engine API, the missing permission)
- **AI assistants (MCP)**: Settings → AI assistants lets Claude Desktop, Claude Code or another MCP client read the clusters you pick, whole clusters or named namespaces. It's off by default and read-only (list, describe, logs, events, manifests, cluster health). Secrets and ConfigMap contents are never shown, and environment values are redacted. The card gives the Claude Desktop config and the `claude mcp add` command; both run `kubebay-engine mcp-stdio`, which reads a token Kubebay keeps in `~/.kubebay/mcp.json` (0600) and replaces when you turn MCP on or rotate it. Turning it off revokes the token. Every call goes to the audit log, the card lists recent ones, and the sidebar shows "AI access on" while it's on. Not available in in-cluster or OIDC mode
- **Overview: why it fails, and since when**: the top five Needs attention rows show the worst pod's last log line (from the crashed run when it has restarted), and a workload's Summary tab shows its warnings over the last hour as 5-minute bars with whether they are new, started a while ago or have gone on all hour. With history recording on, the Summary tab also says how many recorded hours of the last 7 days the workload was broken in ("Broken in 9 of 131 recorded hours, on 4 of 6 recorded days"); the engine records one sparse line per broken workload per hour
- **Scale and restart from the table**: Deployment and StatefulSet rows get Scale… and Restart… in their row menu (DaemonSets get Restart…), each a small dialog that warns when Argo CD or Flux owns the workload and shows a policy rejection in place. `Modal` gains `placement="center"` for such dialogs
- **Faster, friendlier resource tables**: the filter matches every column (Pods: name, namespace, node, IP and status) and ignores case; the count reads "3 of 340" while filtered; `/` focuses the filter, ↑/↓ or j/k move, Enter opens, x selects, Esc clears; the sort is remembered per table; ages show the exact time on hover; Pods gets a row menu (Logs, Shell, Edit YAML, Copy name, Delete) and clickable namespace pills; the + button opens Create Resource on that kind's template
- **Loading states**: a new helm loading icon and `Spinner`, shown while switching clusters; lists load as skeleton rows under their real headers, drawers as skeleton lines, lazily loaded pages as a skeleton page, and tables show a thin progress bar while cached rows refresh
- **`Row`, `Stack`, `DisclosureButton` and `ChoiceCard` in `@kubebay/ui`**: every flex layout in the app uses `Row` or `Stack` with gaps from the spacing scale; sidebar groups announce whether they are expanded and theme cards which one is chosen to screen readers
- **Shared shell components in `@kubebay/ui`**: `StatusPill` + `phaseTone()`, `Tabs`, `NavItem`/`NavSection` + `navItemClass()`, `TextField`, `Select`, `Kbd`, `PageHeader` (with `level` and `live`) and `ContextMenu`. Their styles now live in the package (#12)
- `--kb-on-danger` token in every theme for labels on danger fills (#12)
- **`Drawer` and `Modal` in `@kubebay/ui`**: the Pod, Helm release, Helm chart and resource drawers share one component that closes on Escape (not while you type in a field, the YAML editor or the terminal) and returns focus to where it was; the cluster icon picker is a `Modal` that keeps focus inside until it closes
- **`IconButton`, `SegmentedControl` and `Badge` tones `warn`/`info` in `@kubebay/ui`**: close, pop-out, star and row-menu buttons share one look and always carry an accessible label; the Settings display options and the Workloads and Network Policy view switches are keyboard-navigable radio groups; hand-written tab rows (Pod panel, Helm, cluster icon picker) use `Tabs`
- **`DataTable` and table primitives in `@kubebay/ui`**: every table in the app (resources, pods, Helm, ArgoCD, audit log, port forwards, network policies, cluster picker, cost and right-sizing panels) now shares the ResourceTable design. Also new: `EmptyState`, `InlineBanner`, `KubebayMark`
- `docs/DESIGN_SYSTEM.md` and a CLAUDE.md rule: all UI is built from `@kubebay/ui`, enforced by tests
- **Karpenter safe editing**: an Edit affordance on each NodePool card shows a blast-radius impact banner (nodes/pods/namespaces backed by the pool, spot count, and real PodDisruptionBudget coverage via Kubernetes label-selector matching) and requires typing the NodePool's name to confirm before applying any of three eviction-causing edits (shrinking `spec.limits`, lowering a disruption budget's `nodes` value, or switching `consolidationPolicy` to `WhenEmptyOrUnderutilized`)
- **KEDA ScaledObject wizard**: an "Add ScaledObject" flow in the Autoscaling tab generates a manifest for cron, CPU/memory, or Prometheus triggers, previews it with a live diff, and dry-runs/applies it — always created paused, with scale-to-zero (`minReplicaCount: 0`) gated behind typing the workload's name to confirm, and blocked outright if an HPA already targets the same workload. The Prometheus trigger suggests in-cluster Service candidates for `serverAddress` rather than reusing Kubebay's local Prometheus proxy URL, which resolves to a different address entirely
- **The desktop window follows the theme**: the title bar and the window behind the page take the chosen theme's appearance and colour (or follow macOS for System), and the next launch opens in them instead of flashing the OS default

### Changed
- **Performance budgets fail the build**: the `perf (kind)` CI job now fails when the engine goes over a PRD §6 budget (cold start ≤ 1.5 s, idle RSS ≤ 150 MB, idle CPU ≤ 1%, 10k pods watched ≤ 400 MB), instead of warning. Main had three runs in a row within every budget first; `docs/PERFORMANCE.md` has the numbers
- **Helm 4 and Kubernetes 1.37 libraries** (ADR 0002): the Helm page runs on the Helm 4.3 SDK instead of Helm 3.19.5, which gets no more fixes (Helm 3's security support ends 2027-02-10). client-go and the other `k8s.io` modules move from v0.34.10 to v0.37.1. What you'll notice:
  - New installs are **server-side applied**, Helm 4's default. Upgrades and rollbacks keep the method the release was created with, so releases Helm 3 installed stay client-side.
  - Each revision in a release's History says "server-side apply" or "client-side apply".
  - Releases Helm 3 wrote list and open as before, and each Helm version reads the other's releases.

  A new integration test installs, upgrades, rolls back and uninstalls a chart through the engine on kind (Kubernetes 1.29, 1.34 and 1.37), and reads a release in Helm 3's format. The engine binary is about 8 MB larger, and its idle memory about 9 MB higher (still within the 150 MB budget)
- **Building the engine needs Go 1.26 or later** (was 1.24), which Helm 4 and the Kubernetes 1.37 libraries need. CI, release and Docker builds already used Go 1.26. `make build` uses whatever Go you have installed (`GOTOOLCHAIN=local`), so install Go 1.26 first
- **Building the engine needs Go 1.24 or later** (was 1.22, out of support since February 2025). `go.mod` asks for Go 1.24 at minimum, which the Anthropic Go SDK needs for AI triage, and names Go 1.26.9 as the toolchain, so CI, release and Docker builds use a supported compiler. `make build` still uses whatever Go you have installed (`GOTOOLCHAIN=local`), so install Go 1.24 or later first
- Removed about 800 lines of unused styles and two unrouted pages (the old Home and Overview)
- **Every theme meets WCAG AA**: text reads at 4.5:1 or better on every surface, status pills and button labels reach 4.5:1, and focus rings are solid and at least 3:1. Dawn HC and Dusk HC reach 7:1 for body text with 3:1 control borders. Hues are kept; only lightness moves. Visible changes: Dusk primary buttons use a dark label on cyan, Dawn's accent is a deeper blue (`#0065c9`), VS Code Dark+ uses a lighter blue (`#31a6ff`), and Nord's error red is a pale rose (`#e6c1c4`) (#12, this release)
- The shell renders every page header, toolbar input and select, keycap and sidebar link through `@kubebay/ui`, so the package is the single source of truth for that markup
- Settings theme swatches match each theme's colours
- Ghost and danger buttons match the design system everywhere (an `app.css` override had given them a weaker border and smaller text); the cluster picker's search, table, status and provider badges and row menu use the shared components; provider badges are neutral instead of hand-picked hues that failed contrast in light themes
- Cluster avatars pick black or white initials by contrast with their colour
- **"System" theme follows the OS contrast setting**: with "Increase contrast" on, it picks Dusk HC or Dawn HC
- **Pending has its own colour**: Pending pods use each theme's info hue instead of the warning orange, so they no longer read as warnings

### Fixed
- **A drain that can't reach the cluster says why**: when Kubebay couldn't build a client from a cluster's credentials (a malformed certificate, say), Drain ignored the error, tried to cordon the node anyway and reported the cordon's failure. It now stops before cordoning and reports the client error
- **Helm: no rendered Secrets in the release list**: the release list and history sent every release's rendered manifest to the page on each 12-second refresh, Secret data included, and nothing showed it. They no longer carry manifests (the list for 60 releases went from 71 KB to 13 KB), and the Manifest tab masks each Secret's `data` and `stringData` values, keeping their keys (ADR 0004)
- **Helm acts as you**: Helm read the kubeconfig itself instead of using the connection every other request uses, so it ignored the signed-in identity and, in in-cluster mode, which has no kubeconfig, couldn't work. It now uses that connection, so in-cluster it impersonates the person signed in like every other request. Rollback and uninstall are now in the audit log, like install and upgrade
- **Helm release drawer stays current**: the drawer kept the release as it was when you clicked it, so after an upgrade, a rollback or a failure elsewhere its Rollback buttons pointed at the wrong revision. It now follows the release live, refreshes its history when the release moves on, and says when the release has been uninstalled. History lists the newest revision first (it read v1, v10, v2…)
- **The engine uses far less memory on big clusters**: watching 100,000 pods, it held about 2 GB, five times the PRD's 400 MB budget, and grew while nothing changed. A heap profile found three causes, now fixed:
  - managedFields' field sets, which nothing in Kubebay reads, were most of every object in memory (each entry's manager and time stay);
  - the Cost/Waste sampler fetched every pod in one request every minute, even with the page closed; it now fetches 2,000 at a time;
  - a table's first load copied every object before sending the first, and the cluster's initial list was also sent ahead of it, copied a second time. It is now sent 200 objects at a time, each object once.
  
  The same 100k pods now stay under 400 MB in metadata mode (346 MB at sync, 389 MB once the sampler has run), and at 1.4 to 1.9 GB in full mode, which the Pods page uses, down from 2.6 to 3.2 GB. Tables loaded in metadata mode send about 75% less on first load and sync about twice as fast
- **The Overview's SPOF Radar and Service Health tabs load their data**: a stream that starts switched off (these tabs' PodDisruptionBudgets, Services, EndpointSlices, Ingresses and kube-system ConfigMaps open only when the tab does) never subscribed when it was switched on, so the tabs judged a cluster without them
- **Long tables scroll smoothly**: scrolling the Pods table with 100,000 pods ran at about 37 frames a second in the performance harness. Every row's Age tooltip built a new date formatter, and the select-all box checked every row on every frame, even with nothing selected. It now runs at 55 to 59, against the browser's 60 there. Every resource table shares this code, so they all gain the same
- **A list filtered to several namespaces shows all of them**: picking `shop` and `payments` showed only whichever namespace loaded last, because each namespace's rows replaced the others'. A subscription now arrives as one snapshot holding every namespace. When RBAC refuses one of them, the list says so ("You can't list deployments in payments. Showing shop.", with the API server's reason) and the rest stay live; before, one refused namespace stopped the whole list while its rows stayed on screen marked Live. AI assistants (MCP) asking for something RBAC refuses get the refusal at once instead of a 20-second timeout
- **The container image reports its version**: `kubebay --version` and `/api/version` in the `ghcr.io/rajasardar/kubebay` image said `dev`. A release's image now reports its tag, like the release binaries, and a main build reports `main-<commit>`. The image's engine is also built by the Go release go.mod names (1.26.9), as the release binaries are, instead of whichever Go 1.26 Docker Hub had at build time
- **The local terminal works in released desktop apps**: the release workflow built the desktop app's engine without the `localshell` build tag, so on macOS and Linux the terminal for your own machine said "local shell is not built into this binary" in every downloaded app; only `make build` builds had it. The desktop engine is now built with the tag on every platform (the standalone engine and the container image still never have it). CI's desktop smoke test starts the engine it builds with `--local-shell` and fails unless the shell is available, or, on Windows, which has no local shell, unless the engine gives the platform's own reason
- **Helm installs put every object in the release's namespace**: installing or upgrading a chart from the Helm page put any object whose template has no `namespace:` into the kubeconfig context's namespace (usually `default`), while the release itself was recorded in the namespace you picked. `helm install -n` puts them in the release's namespace, and so does Kubebay now. Charts that template `namespace: {{ .Release.Namespace }}`, as most published charts do, weren't affected
- **Kubebay no longer uses CPU while you're not doing anything**: with a cluster page open, the engine woke every open table's update queue 60 times a second whether or not anything had changed, about 5% of a CPU core on a quiet cluster. The CI performance job flagged it against the PRD's "≈ 0% idle CPU". A table's queue now sleeps until a change arrives and sends it 16 ms later, as before, and the same page now costs about 0.1%
- **Nothing loads from Google any more**: every launch fetched a stylesheet from fonts.googleapis.com, for Inter (which nothing used) and JetBrains Mono (Display settings' third font), telling Google each time Kubebay opened; offline, JetBrains Mono quietly fell back to another font. JetBrains Mono now ships with the app, and the page loads nothing from another origin (a test checks `index.html` and that every font Display settings name is bundled)
- **The YAML editor works offline**: every code editor (YAML tabs, Create resource, Helm values, the KEDA and right-sizing diffs) loaded Monaco from cdn.jsdelivr.net the first time it opened, so with no internet, behind a proxy that blocks it, or in an air-gapped install it never appeared, and each first open told a CDN you were using Kubebay. Monaco now ships in the app: the editor, its features and YAML only, about 4 MB minified, loaded the first time an editor opens. Closing a diff (after Dry-run, or turning off "diff view") no longer throws an uncaught "TextModel got disposed" error
- **Pages that can't read what they need say so too**: the Workloads Overview, Timeline, Right-sizing and Cost / Waste kept their loaders up forever when RBAC didn't let your identity list what they read. Each now says what it can't list ("You can't list pods, nodes, deployments, statefulsets, daemonsets and jobs here.") with the API server's reasons
- **A list you're not allowed to see says so**: when RBAC doesn't let your identity list a kind (say, Deployments across all namespaces), the page said nothing and showed a loading table forever, while the engine retried the list in the background. The engine now stops asking and the list says "You can't list deployments here." with the API server's reason. Opening the page again, for example after your access changes, tries again
- **A Deployment's Rollout tab finds its ReplicaSets again**: the drawer's copy of an object had its `uid` and creation time stripped like the YAML editor's, so the Rollout tab always said "No ReplicaSets found", the Timeline had no rollout revisions, and Summary's Created read "–". Only the editor's YAML leaves them out now
- **Dialogs say what they are**: `Modal` takes a `title`, shown as the dialog's heading with a Close button beside it, and centred dialogs taller than the window scroll inside instead of running off it. Configure Prometheus, Scale and Restart, Remove from list and Kubeconfig sources use it; the first had no visible heading at all
- **Configure Prometheus dialog**: the URL field, Cancel and Save show at once instead of waiting behind a spinner that never ended when the cluster's Services could not be listed. It no longer connects a cluster just to look for services, and is not offered for a broken kubeconfig entry. It opens on the URL already set; saving it empty goes back to the default. It lists the Prometheus server first, without Grafana, Alertmanager or exporters (at most four). A service on port 80 gets `localhost:9090` and `port-forward 9090:80`. Enter saves, the engine's own save error is shown, and the dialog is wide enough for a URL and its port-forward command
- **Clusters page**: it no longer opens blank (`HEADERS is not defined` after the v0.5.0 version bump), and its row menu items work again. A pressed row's scale effect moved the menu mid-click, so no item ran; `ContextMenu` now renders into `document.body`, as `Modal` does
